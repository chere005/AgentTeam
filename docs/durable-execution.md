# Durable execution: checkpoints, effect ledger and recovery

Status: implemented in `src/checkpoints.ts` (fixture and crash-simulation tested; not live-provider tested). The workflow engine decision (XState vs LangGraph) stays open; nothing here installs either.

## Why engine-agnostic

Both candidates are state-transition engines. XState models lifecycle transitions; LangGraph models graph execution with its own checkpointer. What neither gives us is the product-specific part that makes recovery safe: which external effects might have happened, which lease/session/approval belongs to which attempt, and the user's decision when the outcome is unknown. Those facts must live in our SQLite store whichever engine drives transitions, so they are plain entities with no engine types:

- `checkpoint` (append-only; SQLite triggers forbid update and delete, like `validation`). One row per boundary: task started/completed/failed/cancelled/interrupted/blocked/requeued, provider session id, terminal tool call, approval requested/resolved, saved provider output. It stores attempt number, dependency status+result hashes, lease paths, the result text of every terminal attempt (so retries never erase prior evidence) and a human-readable `nextStep`.
- `effect` (ledger). Idempotency-keyed external effects with states `attempted`, `completed`, `uncertain`, `failed` (known not applied). `begin(key)` on a completed key replays the recorded result instead of running; on an in-flight or uncertain key it refuses; only a failed key (or one the user decided to retry) may run again.
- `task-recovery` (mutable cursor): attempt number, provider session id, retry policy, backoff deadline.
- `approval` (persisted request, answer, replay memo).

An XState machine could use `checkpoint.boundary` as its state value and `beforeTransition`/`onTransition` as guards/actions; a LangGraph checkpointer could store its own state blob as `checkpoint.data` and keep using the ledger for effects. Replacing the engine would not change the persisted facts or the API.

## Recovery rules (startup, `RecoveryService.recover`)

- Completed tasks stay completed; nothing re-runs them.
- `attempted` effects lose their process: mutating ones become `uncertain`, non-mutating ones `failed` (safe to retry).
- Leases of the dead process are released (owners are re-derived from state, never double-held); validation slots are released by `ValidationService`.
- A `running` task becomes `interrupted` (resumable, nothing runs by itself) or, if it owns an uncertain effect, `blocked` until the user decides: retry (not applied), mark applied (a provider-run needs the result text and is then replayed without a provider call), or abandon (cancels the task).
- A provider run is mutating when the agent has a write folder or uses ACP. A failure after the run could have started leaves the effect uncertain, except authentication, quota and model-unavailable errors, which prove the provider refused first. Mutating ACP tool calls (`edit`, `delete`, `move`, `execute`) get their own ledger entries.
- Run requests that never started (queued feedback) survive a restart and run once. A chat message that was mid-run still fails, with a ledger entry for mutating runs.
- Pending approvals persist; after a restart they are marked orphaned but stay answerable. The answer is recorded and applied once to the identical request (fingerprint of agent, task, tool title/kind/input, options) raised by the resumed run. A task cannot resume while one of its approvals is unanswered. Chat requests (no task id) never inherit an earlier answer. When a task completes or is cancelled, its still-pending restored approvals are closed (`approval.expired`) since nothing will resume them.

## Retry and resume

`POST /tasks/:id/resume` (interrupted/blocked) and `/retry-from-checkpoint` (failed) requeue through the normal `transitionTask` gates: dependencies, validation gate, workflow pause and limits, resource leases and the invocation cap all apply. Resuming does not spend retry budget; a retry of a failed task starts the next attempt and is bounded by the per-task policy (`PUT /tasks/:id/retry-policy`: `maxAttempts` default 5, exponential backoff `backoffMs`/`backoffFactor` capped by `maxBackoffMs`, opt-in `auto`). Explicit user retries ignore the backoff wait but not `maxAttempts` or an undecided uncertain effect. Resuming a workflow after a limit trip (`/workflows/:id/limits/resume`) requeues only limit-stopped failed tasks whose retry gate allows it; a task whose aborted mutating run left an uncertain effect stays failed for a decision in the Recovery panel. The next run receives a recovery note listing already applied effects and, when recorded, resumes the provider session id (falling back to a fresh session if the connection no longer matches).

## Shared state, artifacts and recovery

`src/shared-state.ts` and `src/artifacts.ts` keep their facts in the same SQLite store, so a restart loses nothing:

- `state-change` is append-only (triggers forbid update/delete). A field's current value is its newest change, so there is no mutable copy to drift. Every change records actor, task and run (`<taskId>#<attempt>`), previous version and value hash.
- Every checkpoint embeds `data.state = {versions, digest}`. `POST /workflows/:id/state/restore` (preview with `GET .../restore-preview`) appends `restore` changes that bring each field back to a checkpoint's content; history is never rewritten, and restoring twice is a no-op. A resumed or retried run is told which fields moved since its last checkpoint.
- Writes are optimistic: the caller names the version it read and a stale base gets `409 state_conflict` naming the current version and who changed it. A task's structured output (a single fenced `agentteam-state` block with `writes` and `artifacts`) is validated before the task completes, then applied in the same transaction as the completion; an invalid schema, denied field, missing required write or version conflict fails the task with that actionable message and writes nothing. The conflict base is the field versions recorded when the run started (`state-run`).
- `artifact` records are immutable. Files are confined to an attached workspace of the producing agent (relative paths, no `..`, no `.git`, symlinks resolved and re-checked, again at preview time) and hashed; previews are bounded (16 KiB default, 256 KiB max). Wolfram results link validation record ids; the listing reports their live (possibly stale) status.
- Fresh-memory runs (`memory: "fresh"` in the task state config) withhold shared state and artifacts but still get the recovery continuation note; they are still version-checked when they write.
- Context passed to a run (selected dependency outputs, readable state, artifact metadata) is size-limited (default 24k characters, 8k per dependency, 4k per field) with a summary line, and wrapped in `<untrusted-data>` elements; it is data, never instructions. Task prompts no longer carry unbounded dependency results.

Known limits: effects are only recorded where AgentTeam observes them (provider runs, chat runs, ACP tool updates); the `agentteam-state` block and context assembly are fixture-tested, not live-provider tested; the HTTP caller is the desktop user (naming `agentId` evaluates permissions as that agent); live provider session resume is unverified.

## Workflow graphs (conditions, deterministic commands, human input, fan-out/join, loops)

Status: `src/workflow-graph-model.ts` (schemas, static validation, pure branch/join/condition rules), `src/workflow-graph-command.ts` (command planning, confinement, execution), `src/workflow-graph.ts` (persistence, engine, recovery, `/graphs*` and `/graph-runs*` routes), UI `ui/components/WorkflowGraphs.tsx` (pane "Workflow graphs", reachable from the canvas toolbar and back via "Agent communication graph"). Fixture and crash-simulation tested (`test/workflow-graph.test.ts`, `e2e/workflow-graph.spec.ts`); not live-provider tested. The graph is separate from the agent communication graph (agents, edges, rules), which only says who may talk to whom.

- Entities: `workflow-graph` (current definition), `workflow-graph-version` (immutable, one per definition change), `graph-run` (mutable per-node cursor holding the definition snapshot it started with) and `graph-step` (immutable executed-path record written once when a step reaches a final outcome; triggers forbid update/delete). Retries append later records (`attempt` 2, ...); loop iterations and re-runs are new `visit`s.
- Node types: `task` (creates an ordinary task), `command` (argv, no model call), `condition` (structured expression, never evaluated as code), `human` (persisted `approval` record plus optional free text), `fanout`, `join`, bounded `loop`. Edges carry the outcome they follow (`success`, `failure`, `cancelled`, `skipped`, `always`, `true`/`false` for conditions, `iterate`/`done` for loops); only a `back` edge into a loop may close a cycle.
- Typed inputs: `inputs: {name: {from: "<node>.<field>" | "state:<key>", type, required}}`. Each node type publishes fixed output fields (`OUTPUT_FIELDS`); shared state is read as the node's agent (per-field reader permissions apply). Values are bounded (16k characters), type-checked, recorded in the step by hash only, and given to agent tasks as `<untrusted-data kind="graph-input">` elements; a command receives an input only as a whole argv element that is never flag-like.
- Static validation (`POST /graphs/validate`, shown live in the editor, repeated by `startRun`, which refuses an invalid graph): cycles, unreachable steps, no entry step, unknown/non-upstream/wrongly typed inputs and unknown state fields, loops without a limit (1..25), without body or back edge, joins that do not merge one fan-out's branches, fan-out with one branch, trigger/source mismatches, command workspace/read-only/cwd/path-escape/shell-form problems, unknown agents. A draft with problems can be saved; it cannot run.
- Dead paths: a step whose incoming edges all resolved without firing is `skipped` (recorded). A join waits for every incoming branch, then `all` completes only if nothing failed or was cancelled, `partial` completes (flagged) with at least `minCompleted` completed branches; never-run branches are ignored unless `skipped: "fail"`. A failed or cancelled step that no edge fired for and no join counted is "unhandled": the run ends `failed` and the step can be retried.
- Gates (no node type bypasses them): a paused workflow, including a limit trip, starts no step of any type; an agent step is a normal task (scheduler, validation gate, mandatory reviews, completion checks, limits, leases); non-task steps wait (`review-required`) for the required reviews of the task steps feeding them; a command takes the same limits check (`enforceStart`, counted as an agent turn) and folder lease as a task start, registers its process on the lease (a crash leaves a draining lease), obeys the live-execution switch and agent human control.
- Commands: the commands a run would execute are listed by `GET /graphs/:id/commands` and `startRun` needs their hash (`confirmCommandsHash`), so editing a command invalidates an earlier confirmation. Spawned without a shell (a node must say `shell: true` for one script string), scrubbed environment (no tokens), working directory and path-like arguments confined to the chosen attached workspace (symlinks resolved, `.git` refused) and to that attachment's file rules and exclusions (on a restricted attachment any argument containing a separator or naming an existing entry is checked, and a `shell: true` script is refused because it cannot be checked path by path), bounded time and output, process-group kill. A run pins each command without an explicit `workspace` to the folder shown when its commands were confirmed. This is path confinement, not an OS sandbox. A `mutating` command needs a write workspace and goes through the effect ledger: exit 0 completes the effect; a failure or kill after it started is `uncertain` and the step waits (no terminal record) for the decision in the Recovery panel (retry, mark applied, abandon); a program that could not be started is `failed`. Non-mutating commands are ledgered as non-mutating and simply run again after a restart. A completed effect is replayed, never re-run.
- Recovery: `Scheduler.start()` calls `graphs.recover()` after task recovery; a command step with no live process consults its effect (completed: replayed; uncertain: waits; failed or lost non-mutating: run again as a new visit, once the old process's lease has drained). Tasks keep their own checkpoints; the graph only re-reads task status.
- Retry from a failed step: allowed while nothing downstream completed or is running; downstream steps that were skipped/failed are reset. A task step uses `retry-from-checkpoint` of the same task (attempt limit, backoff, uncertain effects and all gates apply); a cancelled task or a step whose task could not be created gets a fresh task; commands re-run as a new visit.

Known limits: a limit trip or runtime budget does not abort a running command (it ends by its own timeout or a run cancel); steps cannot write shared state or artifacts; joins always wait for all branches (no early exit or cancelling the rest); loops are do-while (the body runs once before `until` is checked); conditions and typed inputs see at most 32k characters of a step's output (the full result stays on the task/effect); graphs cannot be deleted or archived; live-provider behavior of task steps is only as verified as tasks in general.
